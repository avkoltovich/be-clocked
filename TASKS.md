# Задачи на переписи BeClocked (spec → tasks)

Файл описывает план реализации нового приложения BeClocked на **новом стеке**.
Он разбит на **небольшие, самодостаточные задачи**, рассчитанные на выполнение
**одной локальной LLM-агентом** (MacBook Pro M5 Pro, 48 GB). Каждая задача
уменьшает контекст до минимума: в ней указано, **какие конкретные фрагменты
спецификации** читать для данного шага, и **какие файлы**, которые нужно трогать.

---

## Как этим пользоваться

- **Источник истины** — текущая (as-is) спецификация в `openspec/specs/<модуль>/spec.md`.
  Каждая задача ссылается на **конкретный файл и раздел (Requirement)**, чтобы
  исполняющему агенту не нужно было читать весь код и все спеки сразу.
- Порядок выполнения — **по номерам задач внутри фаз**. Фаза → следующая фаза.
  Внутри фазы задачи независимые, их можно делать в любом порядке.
- Перед каждой задачей — **бюджет контекста**: список из 1–3 файлов/разделов,
  которых достаточно для её выполнения. Не читайте остальное приложение.
- Каждая задача заканчивается **чек-лист приёмки** (из сценариев GIVEN/WHEN/THEN)
  и **критерием «готово»**, который должен быть проверим (тест / build / ручной прогон).
- **Не уводите за рамки**: реализуйте только то, что написано в указанном
  Requirement. Если встретились смежные вещи — вынесите в новую задачу.
- Язык спецификации и артефактов — **русский** (см. `openspec/config.yaml`).
  Технические заголовки и ключевые слова SHALL/MUST остаются на английском.
- Для **UI-задач** компоненты берите по **актуальному API Taiga UI** через
  `@taiga-ui/mcp` / `llms.txt` (настройка — задача 0.3), а не из памяти модели.
  Стек: **Angular 19+ + Taiga UI v5** (см. задачу 0.1).

### Объём задач (почему они небольшие)

Для локального агента лимитирующим фактором является **контекстное окно**, а не
RAM. Поэтому каждая задача рассчитана на ~1–3 минуты чтения и ~30–60 минут работы
агента. Крупную область (например, «протокол») мы сознательно раскололи на
несколько мелких задач, чтобы у агента не переполнялся контекст.

## Как читать старый код → новый подход (RxJS → signals)

- **`src/app/**` — эталон логики, а не копия.** Логика (алгоритмы, инварианты,
  границы, формат времени, порядок состояний) берётся из старого кода и
  подтверждается сценариями `openspec/specs/**`, но **код не переносится
  дословно** — переписываем заново на актуальный Angular.
- **State → signals и standalone.** Старый код использует `BehaviorSubject`
  / `Observable` и `NgModule`. Новый: **standalone-компоненты**, состояние =
  `signal` / `computed` / `linkedSignal` / `resource`, инжекция через `inject()`,
  эффект через `effect()` только там, где нужно. Убираем `.pipe(`, `.subscribe(`,
  `takeUntil`, `ReplaySubject` и `asyncPipe`.
- **Карта переписываний** (найти и перевести при встрече в задаче):

  | Было (`src/app/**`, RxJS) | Стало (Angular 19+ signals) |
  |---|---|
  | `BehaviorSubject<T>`, `.asObservable()`, `.subscribe()` | `toSignal(subject, { initialValue })` или прямой `signal<T>()` |
  | агрегаты через `combineLatest` / `mergeMap` | `computed(() => …)` по сигналам |
  | «одноразовый» `Subject` (emit) | `output<T>()` / `outputRef` или `writableSignal` |
  | `asyncPipe` в шаблонах | сигнал в шаблоне: `{{ count() }}` |
  | инжекция в конструкторе `private svc: Svc` | `private svc = inject(Svc)` |
  | `NgModule` (`app.module.ts`) | **standalone** (без NgModule) |
  | `Zone.js` | **zoneless** (`provideExperimentalZonelessChangeDetection`) по умолчанию — см. 0.1 |

- **Исключения — оставляем как есть** (это логика, а не паттерн): `localStorage`
  persistence (1.2), формат `ЧЧ:ММ:СС.ммм` (6.2), расчёт кругов/DNS/DNF
  (4.4, 5.3, 6.5), порядок переходов статусов (2.3) — порт **логически**, но
  на signal-based API.
- **Каждая задача, где читается legacy-файл, указывает в «бюджете чита» два
  источника**: (a) файл спека (`Requirement`) — источник правды; (b) legacy-файл —
  только как эталон логики для перевода в signals.

## Отслеживание выполнения (как агент отмечает задачи)

Каждая задача имеет статус в чекбоксе в заголовке: `### [ ] N.M …`.
- `[ ]` — не начата, `- [ ]` перевернуть нельзя вперёд без исполнения.
- `[~]` — в работе (агент поставил сам перед тем, как ушёл).
- `[x]` — **сделано и проверено**.

**Правила агенту при выполнении одной задачи** (3 роли — см. `DECISIONS.md` § «Роли и конвейер»):

- **Тимлид (qwen3.8:27b-mlx)** — берёт задачу N.M, читает только её «бюджет чита»,
  переводит заголовок `[ ] → [~]`, формулирует промпт для реализатора,
  и принимает вердикт ревьюера.
- **Реализатор (Recursive Flint)** — реализует **ровно** тот `Requirement`, который
  указан в задаче, **переводит** RxJS → signals/standalone по карте,
  **1 commit** в `feat/rewrite-angular-signals`, conventional-сообщение.
- **Ревьюер (nemotron-3.5-lightning:30b-mlx)** — проверяет diff по 5 критериям
  (см. `DECISIONS.md` → «Критерии ревью»); выдаёт **вердикт** `Approved` / `changes requested`.
- При `changes requested` — реализатор доделывает в том же commit, ревьюер смотрит снова.
- **Тимлид** переворачивает `~ → x` только после `Approved` + записи в `PROGRESS.md`.

Легенда статусов: `~` в работе (реализатор), `x` — сделано и проверено (после
`Approved` ревьюера).

**Шаблон блока «Выполнено»** (тимлид вставляет под критерий «готово» **после** вердикта ревьюера):

```markdown
> **Ветка:** feat/rewrite-angular-signals
> **Реализатор:** Recursive Flint (<runtime: Pi/OpenCode>) — commit `<sha>`
> **Коммит:** `feat(<scope>): implement task N.M <название>`
> **Ревьюер:** nemotron-3.5-lightning:30b-mlx (<runtime>)
> **Вердикт:** Approved | changes requested × N → Approved
> **Проверено:** <команда/тест: ng test / build / E2E, результат зелёный>
> **Таига UI:** по `@taiga-ui/mcp`/`llms.txt` (или legacy — если MCP недоступно)
> **Осталось/след. задачам:** <что заметил, ссылки на смежные>
```

**Общий журнал — файл `PROGRESS.md` в корне.** Каждый запуск дописывает
новую запись (append-only, не править старое) по шаблону: дата, задача, роль
(реализатор/ревьюер), вердикт, что сделано, как проверено, commit. Так вы
получаете историю вне git и не нагружаете контекст на чтение большого файла.

**Обзор «на одном экране»** — grep по чекбоксам в `TASKS.md`:

```bash
grep -n '^### \[' TASKS.md        # весь статус списка
rg '\[x\]' TASKS.md               # что уже сделано
rg '\[ \]' TASKS.md               # что впереди
```

## Фаза 2. Жизненный цикл гонки (Race Lifecycle)

### [ ] 2.1 Тип гонки (Разделка / Групповая) + блокировка после старта

### [ ] 2.2 Имя гонки
- **Бюджет чита**: `openspec/specs/race-lifecycle/spec.md` (Requirement
  **Имя гонки**).
- **Цель**: дефолтное `«Название гонки»`, редактирование только до старта,
  во время гонки — заголовок с именем.
- **Критерий «готово»**: в состоянии `START`/`PAUSE` имя только отображается.

### [ ] 2.3 Переходы состояний гонки
- **Бюджет чита**: `openspec/specs/race-lifecycle/spec.md`
  (Requirement **Состояния гонки**).
- **Цель**: машина состояний `PREPARE → READY → START → PAUSE → FINISH`;
  переход `PREPARE → READY` — по добавлению **первого** участника.
- **Критерий «готово»**: все 5 состояний присутствуют; переход
  `PREPARE → READY` срабатывает ровно при добавлении первого участника.

### [ ] 2.4 Запуск / пауза / полный сброс / автозавершение

  (Requirements **Завершение гонки**, **Сброс гонки**).
- **Цель**: явное завершение и **автоматическое** — когда все участники
  получили `FINISHED` или `DNS` (фиксируется `raceEndTime`); сброс возвращает
  состояние в `PREPARE` с дефолтами (с подтверждением).
- **Критерий «готово»**: автозавершение срабатывает только при условии
  «все = FINISHED|DNS»; сброс реально очищает состояние.

## Правила для исполняющего агента (кратко)

1. **Открывайте только** то, что указано в «Бюджет чита» для текущей задачи.
2. **Реализуйте только** тот Requirement, который назван в задаче.
3. **Проверяйте** чек-лист приёмки и критерий «готово» до перехода.
4. **Не переносите** изменения из смежных областей — это другая задача.
5. **Фиксируйте** выбор целевого стека в `DECISIONS.md` в начале задачи 0.1
   (Angular 19+, standalone, signals, zoneless — см. карту RxJS→signals выше).
6. **Логика берётся из legacy `src/app/**`, но переписывается на signals/standalone.**
   RxJS-паттерны (`.subscribe`, `BehaviorSubject`, `combineLatest`, `asyncPipe`)
   заменяются `signal` / `computed` / `linkedSignal` / `resource` / `output`
   (см. карту в «Как читать старый код → новый подход»). Из legacy читаем только
   логику, не переносим `NgModules` и `BehaviorSubject`.
7. **UI-компоненты берите по актуальному API Taiga UI** через
   MCP-сервер `@taiga-ui/mcp` / `llms.txt` (см. задачу 0.3), а не из памяти
   модели — это предотвращает устаревшие импорты и несовместимость с Taiga v5.
8. **Оформляйте выполнение**: чек-лист + блок «Выполнено» + чекбокс `[x]` в
   заголовке + 1 коммит на задачу (см. раздел «Отслеживание выполнения»),
   затем допишите запись в `PROGRESS.md`.
